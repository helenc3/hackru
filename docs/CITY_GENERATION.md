# Quest-aware Shanghai city generation

> Section 9 browser persistence is superseded by [proposals/server-owned-city-layout.md](../proposals/server-owned-city-layout.md): the server owns committed manifests; the browser remembers only identifiers.

**1. Scope.** Add an opt-in city streaming system that builds neighborhoods as the player walks, using Claude to propose city layouts and the existing renderer to construct them from reusable assets. Replace the existing campaign with the three quests in [NEW_QUESTS.md](NEW_QUESTS.md): buy a drink, find directions to Shanghai Grand Hotel, and ask a passerby to photograph the player at the Huangpu River. This revises the current specification's campaign and exclusion of procedural cities; update the spec and shared contracts during implementation. Retain Mandarin interactions and deterministic quest rules. Create a Shanghai-style starting neighborhood for the new campaign and stream additional neighborhoods beyond it.

**2. Shanghai composition.** Aim for a recognizable Shanghai-inspired city rather than a literal map: mostly level ground, dense streets, mixed residential and commercial blocks, lane-house neighborhoods, apartment compounds, modern office clusters, metro entrances, and waterfront promenades. Use a large connected river corridor and narrower creeks/canals, with parks, bridges, courtyards, street trees, and occasional outer industrial areas. Shanghai's Huangpu River and Suzhou Creek waterfronts provide a reference for the water-and-neighborhood structure ([Shanghai waterfront plans](https://english.shanghai.gov.cn/en-Latest-WhatsNew/20250313/1f9cc793a9124589b599be90be244a84.html)). Treat density and feature frequencies as tunable design choices, with human-reviewed Simplified Chinese signage and no claim of geographic accuracy.

**3. Districts as biomes.** Generate only three broad, contiguous districts: shopping/dining, waterfront, and parkland. Shopping/dining is the default built fabric; lane houses, apartments and offices may appear as building styles rather than separate biomes. Seeded district cells span six chunks, with illustrative targets of 72% shopping/dining, 16% waterfront land, and 12% parks (water corridors reserved separately). The waterfront spans the river banks and their adjacent inland blocks. Spawn and the hotel remain shopping/dining. Fill urban blocks with continuous frontage and aligned interior building rows; use four-to-eight-storey mixed-use storefronts for most frontage. Place trees and furniture at regular eight-metre sidewalk stations, and arrange park features around clear paths instead of scattering greenery over urban lots. All road widths are halved from their original sizes: avenues are 5 metres, streets 3.5 metres, lanes 1.5 metres, and promenades 3 metres. Intersections have no traffic lights.

**4. Build the reusable component library first.** Create a substantial, versioned library of authored React Three Fiber components before enabling live city composition. Start by extracting and parameterizing the existing trees, lanterns, signs, canopies, café/kiosk parts, characters, and shared toon materials. Expand it into at least 60 catalog entries across building shells and façades (lane houses, apartment blocks, shops, cafés, restaurants, offices, and warehouses), storefront modules (doors, windows, awnings, counters, approved signs), street infrastructure (road/sidewalk tiles, corners, crossings, metro entrances, lamps, benches, bollards, and bicycle racks), landscaping (trees, shrubs, planters, parks, and courtyard modules), waterfront modules (riverbanks, promenades, railings, level bridges, and canal edges), and interaction anchors (drink vendors, direction helpers, the hotel, viewpoints, and photo-taking passersby). Entries may share underlying components, but each must provide a useful distinct silhouette, configuration, or gameplay role; color-only duplicates do not count toward the target. Provide several compatible variants for common objects and district-specific building kits so repeated chunks remain visually varied and stylistically coherent.

Each catalog entry must declare a stable asset ID, component/version, concise description, district tags, allowed typed parameters and their ranges, dimensions and footprint rules, collision and walkable geometry, attachment sockets, clearance requirements, approved interaction capabilities, detail levels, and rendering cost estimates. Keep render geometry and server collision metadata tied to the same validated parameters. Separate decorative signs from interaction anchors; labels come from the human-reviewed Simplified Chinese text catalog. Build a component gallery for visual review, including parameter extremes, attachment combinations, and representative streets assembled from each district kit. Review silhouettes, scale, collisions, and repeated-object rendering performance before approving entries. Publish a machine-readable catalog plus compact descriptions and example compositions for Claude; the renderer and seeded fallback generator must use that same library. Creating this library is an explicit implementation deliverable, not an assumption that the current scene already supplies it.

**5. Claude generation contract.** Add a separate server-side city-generation provider using the existing Anthropic SDK setup; keep its API key on the server. Give Claude a chunk coordinate, seed, district constraints, fixed road/water boundary connections, neighboring summaries, an approved asset catalog, and a sanitized quest-relevance summary. Explicitly instruct Claude: “Compose this neighborhood from the supplied reusable component library. Select approved asset IDs and vary only their documented parameters; reuse building kits and attachment sockets to create coherent streets. Do not invent components, geometry, materials, scripts, or asset URLs. If the catalog cannot express a desired feature, choose the nearest approved alternative and report the missing capability separately.” Supply a district-filtered selection from the full library, including all required connector and quest assets, with examples of valid modular assemblies. Request structured JSON describing catalog asset IDs, parameter values, transforms, attachment references, paths, water segments, bridges, decoration, and optional approved interaction references; derive footprints from catalog metadata rather than trusting model-supplied dimensions; never execute generated code or download generated asset URLs. Use Claude's [structured outputs](https://platform.claude.com/docs/en/build-with-claude/structured-outputs), then independently validate geometry, catalog version, asset IDs, parameter ranges, attachment compatibility, bounds, object counts, rendering budgets, connectivity, and gameplay permissions. Reject unknown assets and unsupported parameters; missing capabilities are development proposals, never executable model output. Claude proposes the local composition; deterministic code validates it and builds the meshes and collision data.

Drink vendors are complete serving assemblies: a drink stall or café counter with an attached vendor character and an interaction anchor bound to the stand. Convenience-shop shells do not substitute for serving stands. Reserve NPC body space before surrounding scenery; reject overlaps in either placement order. Commit a stand and character together, roll both back on failure, and preserve or remove both during repair. Render their shared transform and distance detail together, keeping animated characters out of static scenery batches.

**6. Streaming while walking.** Start with 40 × 40 world-unit chunks and a visible 3 × 3 neighborhood, then tune through profiling. Treat the initial 3 × 3 area as the spawn box: generate and validate it once, save its original chunk manifests, and pin them in the world cache. Every return to spawn reconstructs those same chunks from cache with no Claude generation request; walking away, respawning, and quest changes must not invalidate them. Prefetch a surrounding ring, prioritizing chunks in the player's direction of travel; request small batches on chunk-boundary changes rather than every movement frame. Keep movement and dialogue responsive while requests run. Assemble validated chunks offscreen and reveal them before the player reaches them; if they are late, immediately commit a compatible seeded fallback chunk. Once revealed, keep its layout stable rather than replacing it with a late Claude result. Deduplicate requests, bound concurrency, discard superseded results, and unload distant meshes while retaining committed chunk descriptions for consistent revisits.

**7. Streets, water, and traversal.** Establish shared boundary connectors deterministically so roads, sidewalks, creeks, and riverbanks join across chunks regardless of generation order. Place bridges only at valid crossings, reserve clear sidewalks and quest routes, and reject buildings overlapping water, roads, or each other. For the first version, bridges have level walkable decks and water is blocked by collision, preserving the current flat movement model. Build one chunk manifest consumed by both server movement validation and client rendering; the existing fixed scene bounds and colliders must be extended through a proposed shared contract. Validate reachable paths before committing a chunk and use deterministic repair or fallback when needed.

**8. Gentle quest relevance.** Use the active quest and eligible interactions defined in [NEW_QUESTS.md](NEW_QUESTS.md) to tag features as drink vendors, direction-giving NPCs, hotel landmarks, Huangpu waterfront viewpoints, or photo-taking passersby. Track the last time the player actually encountered each relevant category using proximity and visibility, rather than when it was generated. After roughly three minutes of active exploration or six newly visited chunks without a relevant encounter, raise that category's placement weight gradually, capped at 1.5× its baseline, then normalize eligible weights; reset the boost after an encounter. Send these preferences to Claude and enforce quotas through seeded server selection, only in unseen chunks and compatible districts. Reserve one persistent hotel destination and a connected Huangpu River corridor early; guarantee reachable quest opportunities within a configurable exploration distance using deterministic placement or fallback, since probability alone cannot ensure completion. Claude may propose approved vendors, helpers, and viewpoints, but cannot relocate revealed landmarks, invent destination facts, or grant purchases, photos, or completion. All three new quests use this bias; the previous connection boss is removed.

**9. Reliability and cost.** Cache committed manifests by persistent world ID and chunk coordinate, recording seed, generator version, quest-context snapshot, and content hash; a seed alone cannot reproduce a live model response. Store original manifests in the authoritative server world store, with the same process-local lifetime as quest progress, player location, and inventory. Clients request committed chunks around the player on demand, including after reload; browser storage remembers only the world and session identifiers, never terrain manifests. A server restart clears both session progress and committed terrain. Look up committed chunks before scheduling generation; quest changes and session restarts within the same world never regenerate cached terrain. Keep mutable quest, inventory, and NPC interaction state separate from original terrain manifests so restoring geometry does not reset progress. Unload meshes independently of saved manifests, and reserve cache eviction of spawn terrain for an explicit new-world/reset action. An incompatible generator version needs an explicit migration or reset rather than silently regenerating spawn. Reuse approved templates when Claude times out, refuses, returns invalid geometry, or reaches a session budget. Start with two concurrent requests, an eight-second request deadline, one bounded retry within that deadline, and configurable token/call caps; tune from measured latency and usage rather than assumed pricing. Prefer instanced meshes, distance-based detail, and bounded asset counts. Log validation failures, fallback rate, generation latency, and provider usage without secrets or raw conversations; use fixture generation by default in tests.

**10. Delivery and acceptance.** First update the campaign specification from [NEW_QUESTS.md](NEW_QUESTS.md) and propose chunk, movement, interaction, and photo contracts; then create and visually approve the reusable component library, its metadata, gallery, and example district assemblies. Implement seeded district/road/water planning and fixture streaming using that library, add Claude composition behind a feature flag, and finally enable quest bias and visual polish. Accept the library only when it contains at least 60 approved useful entries spanning every listed category, each entry renders in the gallery with valid collision metadata, common objects have meaningful variants, and representative 3 × 3 fixture neighborhoods meet documented rendering budgets. Verify that both Claude manifests and fallback manifests use only catalog assets and allowed parameters, unknown IDs and incompatible attachments are rejected, and catalog versions are recorded with cached manifests. Verify that crossing chunk boundaries has no seams or blocked routes, revisiting preserves layouts, leaving and returning to spawn or reloading the same world produces zero spawn-generation calls and identical terrain without resetting quest state, generation order cannot alter shared connectors, relevant-feature frequency rises modestly after prolonged absence, and late/error responses never interrupt play. Replace old campaign-specific acceptance tests with the three new quest journeys; retain applicable world, voice, and repository checks, and add targeted tests for collisions, budgets, fallback, truthful directions, reachable objectives, and NPC-triggered photo capture. Finish with a manually reviewed Shanghai-style exploration route and a live Claude smoke test, clearly distinguishing fixture results from live generation.
